# Decision log

- **Cleaned before analysing.** 30 exact duplicate rows removed; 4 status spellings fixed ("Rto", "delivered", trailing space); 1 IN_TRANSIT order dropped (no outcome yet); phones normalised ("+91 xxxxx xxxxx" is valid, 9-digit numbers are not); 4 missing cities filled from the state's top city; 12 missing pincodes kept (flagged, not guessed). *Alternative: drop all messy rows - rejected, it would delete real orders and bias the sample.*
- **Optimise rupees, not RTO rate.** One RTO costs Rs169.4 (65+65+25+8% x 180). A delivered average order earns 62% x 649 = Rs402. So shipping is worth it until risk ~70%. Cancel bars are therefore high and never sit below the per-order break-even. *Alternative: Ops' "cancel anything risky" - replayed on September it loses Rs25k-100k/month in realised terms.*
- **Model = logistic regression.** Alternatives: gradient boosting (+ maybe 0.01-0.03 AUC on 2k rows, but un-explainable to ops); hard rules only (can't weigh city vs address vs history). Chose LR because every score decomposes into reasons an ops person can read. Out-of-sample AUC 0.72; predicted vs actual risk matches in every quintile.
- **No pincode blacklist.** 1,066 distinct pincodes in 1,987 orders, 30 with 5+ orders, none with 10+. Pincode history is noise. City-level (19 cities, 20-200 orders each) is the finest level with signal. *Alternative: smoothed pincode target-encoding - rejected, would mostly learn noise.*
- **Hinglish is not a risk flag.** Hinglish-landmark addresses return 30% vs 23% structured, but that is a smaller-city effect (within big cities 21% vs 18%). The LLM/heuristic only separates real-but-needs-a-call from junk.
- **LLM scope.** Address classification, fake names, and (in the flow) odd free-text replies. Everything numeric is code. The LLM output is cached and falls back to a regex so a model outage never blocks orders. Output is a closed set of labels, not free text, so it can't invent a score.
- **Two cancel bars (Marketing guard).** First-time 90%, repeat 75%, plus automatic floor at break-even and a hard hold after 2 earlier returns (76% RTO). First-time customers who look risky go to WhatsApp confirmation instead, which also filters fake numbers for free (no reply -> cancel).
- **Thresholds picked by cross-validation on Apr-Aug only**, then tested on September. The grid favoured nudging from 20%; I set 25% because the gain is small and rests on my acceptance assumptions - less customer friction for a Rs2k/month difference.
- **Discount scales with risk (5% / 9% / 12%, Rs30-90).** Expected-profit grid in `run.py discount`: riskier orders justify a bigger discount because the avoided loss is bigger. Cap Rs90 so the discount never exceeds half the Rs169 RTO cost.
- **Nudge decliners keep COD.** Forcing prepaid on a mild-risk (25-50%) order would hurt conversion; they ship as COD. Silent 24h on a nudge -> ship COD. Silent 24h on a confirm order (>=50% risk) -> cancel with a polite reorder message.
- **WhatsApp language by state** (Hinglish for UP, Bihar, MP, Rajasthan, Delhi; English elsewhere) - editable in rules.yaml. One reminder at 4h, only 9am-9pm. Three unclear replies -> human call.
- **Unverifiable assumptions are labelled** (reply rate 60%, confirmed customers return at half the scored rate, 34% prepaid acceptance at ~9% off, 20% safer acceptors). `run.py sensitivity` reports the range: Rs0.7k to Rs25.5k/month, so the honest answer is "positive, size unknown until tested".
- **Dashboard shows estimates**, because yesterday's orders have no outcome yet. "Yesterday" = latest day in the data (30 Sep).
- **Not built:** real WhatsApp/Shopify/payment integration, address auto-correction, courier routing, weekly retraining job.
